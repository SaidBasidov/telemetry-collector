# SCADA Telemetry Collector

Сервис пакетного сохранения телеметрии в PostgreSQL с HTTP API, фоновым эмулятором датчиков и React-интерфейсом.

Стек: .NET 10 / C#, ASP.NET Core Minimal API, Npgsql 10, PostgreSQL 18, React, Vite, Nginx, Docker Compose.

## Запуск через Docker

Нужен Docker с Docker Compose, например Docker Desktop. Для полного запуска устанавливать .NET и Node.js на компьютер не требуется.

Склонируйте репозиторий, перейдите в его корень и выполните:

```bash
docker compose up --build -d --wait
```

| Компонент | Адрес |
| --- | --- |
| Интерфейс | http://127.0.0.1:8080 |
| API напрямую | http://127.0.0.1:5000 |
| API через Nginx | http://127.0.0.1:8080/api/tags/5/latest |
| PostgreSQL с компьютера | `127.0.0.1:5432` |

При первом запуске скачиваются образы и собираются приложения. PostgreSQL выполняет `sql/init.sql` при инициализации **нового** тома. API запускается после проверки готовности PostgreSQL. У API и фронтенда отдельные healthcheck не заданы: `--wait` подтверждает запуск этих контейнеров, но не заменяет проверку HTTP-запроса.

Через секунду после старта сборщик начинает добавлять измерения датчиков 1–100. В интерфейсе выберите датчик № 5 и нажмите «Получить измерение». История по умолчанию использует последний час на момент открытия страницы. Обновление данных выполняется кнопками.

```bash
docker compose ps
docker compose logs --tail 20 api
docker compose logs -f --tail 20 api
```

Control + C при просмотре `logs -f` останавливает только просмотр журнала.

Остановить и снова запустить приложение:

```bash
docker compose stop
docker compose up -d --wait
```

Данные сохраняются в именованном томе `postgres_data`. `docker compose down` удаляет контейнеры и сеть, сохраняя том. Команда `docker compose down -v` также удаляет том **со всеми измерениями**. SQL инициализации не применяется повторно к существующей базе.

После изменения кода выполните `docker compose up --build -d --wait`.

## Структура и зависимости

| Путь | Назначение |
| --- | --- |
| `src/Telemetry.Core` | Модель, интерфейс хранилища, проверки в `TelemetryService` |
| `src/Telemetry.Infrastructure` | Npgsql, SQL и `PostgresTelemetryStore` |
| `src/Telemetry.Api` | HTTP, входная модель, DI, фоновый сборщик |
| `src/Telemetry.Console` | Учебный консольный пример; не входит в Docker-развёртывание |
| `frontend` | React, Vite для разработки, Nginx для Docker |
| `sql/init.sql` | Таблица, ограничения, индекс `(tag_id, timestamp DESC)` |
| `scripts/check-batch.mjs` | Проверка размера пачки через HTTP |
| `tests/Telemetry.IntegrationChecks` | Проверка хранилища в изолированной схеме PostgreSQL |

HTTP-обработчик вызывает `TelemetryService`, сервис использует `ITelemetryStore`, а `PostgresTelemetryStore` выполняет SQL. Конструкторы получают зависимости через встроенный DI. Источник соединений, сервис и хранилище зарегистрированы как singleton; команды, reader, соединения и списки создаются локально для отдельных операций.

## API

### POST /api/telemetry/batch

Принимает JSON-массив от 1 до 1000 измерений. Все четыре поля обязательны: положительный `tagId` типа int, конечное числовое `value`, `quality` 0 или 1 и `timestamp` в ISO 8601. Для времени используйте `Z` либо явное смещение; перед сохранением оно переводится в UTC.

```bash
curl -i -X POST 'http://127.0.0.1:8080/api/telemetry/batch' \
  -H 'Content-Type: application/json' \
  -d '[
    {"tagId":200,"value":60.5,"quality":1,"timestamp":"2026-10-26T10:00:00Z"},
    {"tagId":200,"value":61.2,"quality":0,"timestamp":"2026-10-26T10:00:01Z"}
  ]'
```

Успех: `200 OK`, `{"saved":2}`. Неверные данные: `400`. `id` генерирует PostgreSQL. Повторная отправка одинаковых измерений создаёт новые записи; дедупликации нет.

Цикл только подготавливает `NpgsqlBatchCommand` в памяти. После цикла выполняется **один** `NpgsqlBatch.ExecuteNonQueryAsync`. Стандартная неявная транзакция Npgsql откатывает всю пачку при ошибке SQL. Одиночные INSERT в цикле не выполняются. [Документация Npgsql](https://www.npgsql.org/doc/basic-usage.html#batching).

### GET /api/tags/{tagId}/latest

```bash
curl -i 'http://127.0.0.1:8080/api/tags/200/latest'
```

Успех: `200` и объект с полями `tagId`, `value`, `quality`, `timestamp`. Если измерений нет — `404`; неположительный номер датчика — `400`.

Сортировка: `timestamp DESC, id DESC`. При одинаковом времени выбирается запись с большим `id`. Качество 0 не исключает запись из результата.

### GET /api/tags/{tagId}/history

```bash
curl -i 'http://127.0.0.1:8080/api/tags/200/history?from=2026-10-26T10:00:00Z&to=2026-10-26T11:00:00Z&limit=10'
```

`from` и `to` обязательны. Обе границы включены; начало не может быть позже конца. `limit` по умолчанию равен 100, должен быть положительным. В интерфейсе можно выбрать до 1000 строк; отдельного верхнего ограничения `limit` в API пока нет.

Успех: `200` и массив от новых записей к старым; при отсутствии данных — `[]`. Некорректные параметры — `400`.

## Сборщик и настройки

`BackgroundService` работает в процессе API. `PeriodicTimer` задаёт интервал 1 секунду; каждый тик создаёт по записи для тегов 1–100. Значения случайные от 0 до 100 с округлением до двух знаков, качество 0 примерно в 10% случаев. Время пачки — UTC.

Пачки обрабатываются последовательно. Если запись длится дольше секунды, параллельные операции не запускаются и пропущенные тики не накапливаются. При ошибке Npgsql ошибка записывается в журнал, следующая попытка сохраняет новую пачку. Очереди повторной доставки нет. Штатная остановка передаёт токен отмены таймеру и сохранению. Токены HTTP-запросов передаются во все три операции хранилища.

Настройки в `src/Telemetry.Api/appsettings.json`:

- `ConnectionStrings:Telemetry` — строка подключения;
- `Collector:Enabled` — включение сборщика, по умолчанию `true`.

Переменные окружения `ConnectionStrings__Telemetry` и `Collector__Enabled` переопределяют настройки. Для отключения генерации в Docker добавьте `Collector__Enabled: "false"` в `environment` сервиса `api`, затем выполните `docker compose up -d --wait`.

Внутри Compose API подключается к `Host=db;Port=5432`; с компьютера используется `Host=127.0.0.1;Port=5432`. Порт 5000 компьютера направлен на 8080 контейнера API, порт 8080 компьютера — на 80 Nginx. Nginx передаёт `/api/...` сервису `api`.

Учётные данные `telemetry / telemetry_local` предназначены для локальной демонстрации. Авторизации, очистки старых данных и дедупликации в проекте нет. Сборщик добавляет около 6000 записей в минуту при нормальной работе; остановите окружение, когда оно не используется.

## Проверки

### Размер пачки через HTTP

При работающем приложении и установленном Node.js 22.12+:

```bash
node scripts/check-batch.mjs
```

Проверяется сохранение/чтение 1000 записей, отклонение 1001 без сохранения и отклонение пустой пачки. Каждый запуск оставляет 1000 тестовых записей для случайного датчика вне диапазона сборщика. Адрес можно изменить переменной `TELEMETRY_BASE_URL`.

### Откат при ошибке PostgreSQL

Без установки локального .NET SDK:

```bash
docker compose --profile checks run --build --rm checks
```

Контейнер `checks` не запускается при обычном `docker compose up`. Проверки вызывают настоящий `PostgresTelemetryStore` в отдельной схеме `telemetry_check_<guid>`, создаваемой из `sql/init.sql`.

Временное дополнительное ограничение БД отклоняет вторую запись тестовой пачки. Проверяется откат всех новых записей, сохранность прежних и возможность последующей записи. Это ошибка непосредственно PostgreSQL, а не конструктора модели. Дополнительно проверяются одинаковые timestamp, границы периода, порядок, лимит, отсутствие данных и предварительно отменённые токены.

Схема удаляется в `finally`; `public.telemetry_records` не изменяется. При принудительном уничтожении процесса схема может остаться; её имя выводится в журнал.

С установленным .NET 10 SDK и работающей базой:

```bash
dotnet run --project tests/Telemetry.IntegrationChecks
```

Только проверка модели, без PostgreSQL:

```bash
dotnet run --project tests/Telemetry.IntegrationChecks -- --model-only
```

## Локальная разработка

Нужны .NET 10 SDK, Node.js 22.12+ и npm. Из корня репозитория:

```bash
docker compose stop frontend api
docker compose up -d --wait db
dotnet run --project src/Telemetry.Api --no-launch-profile --urls http://127.0.0.1:5000
```

В другом терминале из папки проекта:

```bash
cd frontend
npm ci
npm run dev
```

Адрес разработки: http://127.0.0.1:5173. Vite передаёт `/api` на локальный порт 5000. Поля периода и таблица используют часовой пояс браузера; запросы истории отправляются в UTC.
